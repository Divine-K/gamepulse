# API Guide: conventions and endpoint plan

This is the design contract for Phases 3 to 7. The interactive reference will be generated by FastAPI at `/docs` (Swagger) and `/openapi.json`.

## Conventions

- **Base path:** `/api/v1`. A breaking change means a new `/api/v2`.
- **Format:** JSON, UTF-8. Field names are `snake_case`. IDs are UUID strings. Timestamps are ISO 8601 UTC (`2026-11-16T19:36:00Z`).
- **Two route groups:**
  - **Dashboard API** uses `Authorization: Bearer <jwt>` and has `game_id` in the path. Ownership is checked.
  - **Game API** uses `X-API-Key: gp_<prefix>_<secret>` and has no `game_id`, because the key identifies the game.
- **Status codes:** `200` OK, `201` created, `204` no content, `400` malformed, `401` unauthenticated, `403` forbidden role, `404` not found (including other tenants' resources), `409` conflict or invalid state transition, `422` validation, `429` rate limited.
- **Errors:** one envelope everywhere.

```json
{
  "error": {
    "code": "session_already_ended",
    "message": "Session has already ended.",
    "details": [],
    "request_id": "b1f0c1e0-..."
  }
}
```

- **Pagination:** `?limit=50&offset=0` (max limit 100) returns `{"items": [...], "total": 123, "limit": 50, "offset": 0}`.
- **Sorting and filtering:** `?sort=-created_at` (a leading `-` means descending) plus resource-specific filters like `?status=active&q=ada`. Allowed sort fields are whitelisted.
- **Idempotency:** `POST` endpoints that create sessions or ingest events accept an `Idempotency-Key` header. Replaying the same key returns the original result (`200` with the stored resource) and creates nothing new.
- **Rate limiting:** fixed window per API key in Redis (default 600 requests/minute, configurable). Headers: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `Retry-After` on `429`.
- **Request tracing:** every response carries `X-Request-ID`.

## Authentication flows

- **Developer:** `POST /auth/register` then `POST /auth/login` returns `{access_token, token_type, expires_in}`. The token has claims `sub` (developer id), `role`, `exp`. Passwords use Argon2id.
- **Game:** a developer creates a game and then an API key. The full key is returned **once** in the create or rotate response. Afterwards only `key_prefix` and metadata are visible. Revoked keys return `401`.
- **WebSocket:** connect, then send `{"type":"auth","token":"<jwt>"}` as the first message.

## Endpoint plan

### Dashboard API (JWT)

| Method | Path | Purpose |
|---|---|---|
| POST | `/auth/register`, `/auth/login` | Create a developer, obtain a token |
| GET, PATCH | `/developers/me` | Profile |
| GET, POST | `/games` | List and create games |
| GET, PATCH, DELETE | `/games/{game_id}` | View, edit, soft-delete |
| GET, POST | `/games/{game_id}/api-keys` | List and create keys |
| POST | `/games/{game_id}/api-keys/{key_id}/rotate` | Rotate (returns new secret once) |
| DELETE | `/games/{game_id}/api-keys/{key_id}` | Revoke |
| GET | `/games/{game_id}/players`, `/players/{player_id}` (+ `/sessions`, `/achievements`, `/events`) | Browse |
| GET | `/games/{game_id}/sessions`, `/sessions/{session_id}` | Browse, filter by status |
| GET | `/games/{game_id}/leaderboards/{metric}` | Ranked players |
| GET, POST, PATCH, DELETE | `/games/{game_id}/achievements` | Definitions |
| GET | `/games/{game_id}/events` | Event log |
| GET | `/games/{game_id}/analytics/{overview,engagement,retention,scores,achievements}` | Analytics |
| POST, DELETE | `/games/{game_id}/simulator/...` | Simulator helpers and cleanup (`is_simulated` rows only) |
| WS | `/ws/games/{game_id}` | Live updates |

### Game API (API key)

| Method | Path | Purpose |
|---|---|---|
| POST | `/game/players` | Register a player (idempotent by `external_id`) |
| GET | `/game/players/{external_id}` | Player profile and stats |
| POST | `/game/sessions` | Start a session |
| POST | `/game/sessions/{session_id}/heartbeat` | Keep the session alive |
| POST | `/game/sessions/{session_id}/end` | Complete with score and result |
| POST | `/game/scores` | Submit a score |
| POST | `/game/events` | Ingest an event (`custom_*` types allowed) |
| GET | `/game/leaderboards/{metric}` | Public ranking |
| GET | `/game/players/{external_id}/achievements` | Player achievements |
| GET | `/game/achievements` | Achievement catalogue |

## Event types (ingestion)

Known types (payload validated): `player_registered`, `session_started`, `session_ended`, `score_submitted`, `achievement_unlocked`, `player_level_up`. Any type starting with `custom_` accepts free-form JSON (max 8 KB).

## Implemented in Phases 5 and 6

- **Scores:** `POST /game/scores` appends to a ledger. With a `session_id` and category `score` it also sets the session's live score. `POST /game/sessions/{id}/end` takes an optional final `score` (default: the live score) and returns `unlocked_achievements`.
- **Leaderboards:** `GET /game/leaderboards/{metric}` and `GET /games/{game_id}/leaderboards/{metric}`. Metrics: `total_score`, `best_score`, `wins`, `achievements`, `completed_sessions`, or `category:<name>`. Query: `limit`, `offset`, `q`, `min_value`, `order`, `period` (category metrics only). Ranks are competition ranks (ties share a rank) computed before search filtering. `GET /game/leaderboards/{metric}/players/{external_id}` returns one player's rank.
- **Achievements:** each new game is seeded with First Game, Dedicated Player, High Scorer, Veteran, Winner and an opt-in Champion. Condition types: `sessions_completed`, `score_reached`, `total_play_seconds`, `wins`, `leaderboard_rank`. Awards are permanent and unique per player, enforced by a database constraint. Editing a threshold applies to future evaluations (at a player's next session end).

## Real-time (Phase 7)

- `WS /api/v1/ws/games/{game_id}`: live event stream for the game's owner. First message must be `{"type":"auth","token":"<jwt>"}`. See `docs/architecture.md` for the protocol, close codes and event types.
- `GET /api/v1/games/{game_id}/live`: `{active_players, source: "redis"|"postgres", dashboards_connected}`.

## Events and analytics (Phase 8.5)

### Event ingestion
`POST /api/v1/game/events` (API key; optional `Idempotency-Key`; rate limited per game, default 600/min).

- **Allowed types:** `player_level_up` (payload `{level, previous_level?}`, validated) and any `custom_<name>` (free-form JSON payload, max 8 KB).
- **Reserved types:** `player_registered`, `session_started`, `session_ended`, `score_submitted` and `achievement_unlocked` are recorded automatically in the same database transaction as the action itself, so they cannot be submitted (422 `reserved_event_type`). Replays and idempotent retries never create duplicates.
- `player_external_id` and `session_id` are optional but must belong to the calling game (404 otherwise). `occurred_at` must be within the last 7 days and not in the future.
- A stored custom event is pushed to dashboards as `event.received`.

`GET /api/v1/games/{game_id}/events` is the event log (newest first). Filters: `event_type`, `player_id` (a player's timeline), `session_id`, `since`, `until`, `include_simulated`.

### Analytics (all computed from the `events`, `game_sessions`, `players` and `player_achievements` tables)

| Endpoint | Returns |
|---|---|
| `GET /games/{id}/analytics/overview?days=30` | Totals, daily (24h) and monthly (30d) active players, currently active players, plus the selected period next to the previous period for trends |
| `GET .../analytics/engagement?days=30` | One point per UTC day: active players, new players, sessions started and completed, average session duration, events (quiet days appear as zeros) |
| `GET .../analytics/retention` | Day-1, day-7 and day-30 retention. `rate` is `null` until players are old enough |
| `GET .../analytics/scores?buckets=10` | Completed-session score distribution: count, average, median, p90 and contiguous buckets |
| `GET .../analytics/achievements?days=30` | Unlock count and rate per achievement plus unlocks per day |

All accept `include_simulated=false` to exclude simulator data. `GET /game/analytics/overview` exposes the overview to API-key callers.

**Definitions.** *Active player*: a player with at least one event in the window. *Day-N retention*: of players registered at least N days ago, the share who have an event between N and N+1 days after registering. Score statistics use completed sessions only.
